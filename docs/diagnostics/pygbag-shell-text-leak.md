# Pygbag Shell Text Leak Incident Report

## Metadata

- Date: 2026-06-16
- Severity: Release-blocking
- Root cause class: Incomplete code extraction during refactoring
- Detected by: Physical iPhone Safari test
- Affected users: All visitors to Pygbag game pages on any browser

## User-visible symptom

Raw JavaScript source rendered visibly as body text around the game canvas on iPhone Safari. The user also observed corrupted non-English characters in a loading message before the game appeared.

## Root cause

When the debug panel was extracted from per-game inline code into a shared external script (`public/play/shared/debug-panel.js`), the old inline code was left behind in all three Pygbag game shells:

- `public/play/cannonball-clash/index.html`
- `public/play/treasure-cove/index.html`
- `public/play/krakens-wake/index.html`

Each file contained the old inline debug-panel implementation **after** the closing `</script>` tag of the external `debug-panel.js` include, without an opening `<script>` tag. The browser treated this code as visible body text:

```js
content.style.cssText = 'white-space: pre-wrap; ...';
function renderTab(tab) { ... }
bridgeCalls.slice(-10)...
refreshInterval = setInterval(...)
```

Additionally, all three shells had invalid document structure — `<script>` blocks appeared before `<head>`, and `<meta charset="UTF-8">` was positioned after large inline scripts, beyond the first 1024 bytes of the document. This created cross-browser encoding risk: browsers that see non-ASCII characters before a charset declaration may fall back to a system codepage, producing mojibake.

## Affected games

All three Pygbag browser games:

- Cannonball Clash
- Treasure Cove
- Kraken's Wake

The Phaser-based game (Race to Treasure Island) was not affected — it uses a different HTML shell generated by Astro.

## Why desktop testing obscured it

Desktop Chromium and Firefox parse the malformed HTML more leniently than Safari. They:

- Apply implicit charset detection heuristics
- Visually hide some text nodes through CSS layout quirks
- Do not visibly display raw `<script>`-body text in the viewport in the same way

The leaked code was still present in the DOM on desktop browsers but was less visible because:

1. The leaked content was pushed to the bottom of the document by later elements
2. Desktop viewports are wider, reducing reflow artifacts
3. Chromium's parser is more forgiving of structural errors

## Why current tests passed

| Test                                           | What it checked                                                 | Why it passed                               |
| ---------------------------------------------- | --------------------------------------------------------------- | ------------------------------------------- |
| `check-browser-game-shells.mjs`                | Presence of expected patterns (INLINE_SCRIPT, cross_file, etc.) | Did not test for absence of leaked patterns |
| `check-built-html-structure.mjs`               | DOCTYPE, `<meta charset>`, canvas presence                      | Did not parse DOM text content              |
| `tests/browser-games.spec.ts`                  | Element existence (canvas, infobox, etc.)                       | Did not assert on body text content         |
| `tests/a11y.spec.ts`                           | Accessibility violations via axe-core                           | Did not inspect raw text                    |
| `tests/mobile-game-layout.spec.ts`             | Geometry and visibility of controls                             | Did not check for text leaks                |
| `scripts/capture-browser-game-screenshots.mjs` | Canvas rendering after runtime start                            | Actively hides shell UI before capture      |

**Principle violated:** Expected elements existing does not prove unexpected content is absent.

## Structural fix

All three Pygbag shells were rewritten to conform to valid HTML5 document structure:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" ... />
    <title>...</title>
    resource hints stylesheets inline startup script Pygbag module script
  </head>
  <body>
    visible shell markup runtime support scripts
  </body>
</html>
```

Specific changes:

1. Removed all orphaned debug-panel source code from all three shells
2. Moved `<head>` opening tag before all scripts and content
3. `<meta charset="UTF-8">` is now the first child of `<head>`, within the first 1024 bytes
4. `<html lang="en">` (was `"en-us"`)
5. Exactly one `<head>` and one `<body>`
6. All script tags balanced with matching open/close
7. Only external reference to `debug-panel.js` retained

## Encoding fix

- Charset declaration moved to first position in `<head>`
- All three files validated as strict UTF-8 (no mojibake sequences)
- User-facing copy uses ASCII punctuation for pre-boot prose

## New negative tests

### Static source integrity (`scripts/check-game-shell-integrity.mjs`)

- Valid UTF-8 with fatal decode
- `<meta charset="UTF-8">` within first 1024 bytes
- DOCTYPE before `<html>`, `<head>` before `<body>`
- Script tag balance (opens == closes)
- Exactly 1 `debug-panel.js` reference
- No inline debug signatures in source
- No non-whitespace direct body text nodes (via JSDOM)
- No duplicate element IDs
- Required shell elements present
- Cross-shell structural parity

### Browser shell integrity (`tests/game-shell-integrity.spec.ts`)

- `document.characterSet` equals "UTF-8"
- No leaked JavaScript signatures in rendered body text
- No non-whitespace direct body text nodes (via DOM API)
- Expected loading copy matches exactly
- No mojibake patterns in rendered text
- Controls hint contains game-appropriate text
- Infobox populated with loading copy
- Loading API: set() uses textContent (safe from HTML injection)
- Loading API: error() displays text safely
- Loading API: ready() hides overlay
- Loads on chromium-desktop, mobile-safari, ipad-landscape

### CI additions

- `shell-integrity` job: static source check (no browser, ~5s)
- `shell-test` job: Playwright game-shell-integrity tests on chromium + WebKit + iPad
